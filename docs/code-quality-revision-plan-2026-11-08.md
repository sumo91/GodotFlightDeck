## R1 统一性能预算定义

将预算名称、源指标、比较方向和单位换算放入一个小模块，供计划校验与预算计算共同使用。保留已有指标和原始帧耗时语义，补齐两个帧耗时预算；不改项目限制值、不剔除慢帧。

本轮保持其他未知字段的现有兼容政策，避免顺带改变所有 legacy 配置的接受范围。两项已支持预算在 legacy 和 named profile 中必须保留，并进入实际评估与结果报告。

验证方法：

- legacy 和 named profile 使用相同两项预算，解析后的 benchmark stage 均保留名称和值。
- 用固定报告验证低于、等于、高于上限，以及平均帧正常但最慢帧超限的情况；等于 `Lte` 上限应通过。
- 通过完整 Verify 路径注入有效的 benchmark 报告：超限返回 `FAILED / performance_budget`，报告列出实际值与限制。仅测试白名单接受不算完成。
- 缺失指标或报告时不能通过；基础设施或报告问题保留对应分类。检查原有 FPS、内存换算等预算没有改变。

建议新增 `mcp/performance-budgets.test.mjs`，复用现有临时项目和模拟引擎方式。真实 Godot smoke 只验证指标从探针到报告的连通性，精确阈值判断使用固定数值，避免机器负载导致测试不稳定。

## R3 修复 Pi 写操作并共享参数转换

先在现有 Pi 路径补齐参数。预检继续执行参数校验；只有现有 Pi 确认成功后，执行调用才携带破坏性动作所需的 `--apply`。batch 的 `commit: false` 保持预览，`commit: true` 在确认成功后提交。

随后提取一个共享 argv 生成函数，接收已校验参数、项目路径及内部报告或 batch 文件路径。MCP 与 Pi 保留各自的授权、schema 校验、临时文件创建和清理；共享函数只负责生成参数，不创建文件、不启动进程、不作授权决定。保留已有公开字段、默认值以及明确的入口差异，例如 MCP 长 scenario 的上限。

验证方法：

- 参数表覆盖 batch 默认值、false、true；delete、resource-delete、cleanup-sessions 的显式执行标志。
- JSON 的负数、布尔、null、数组、对象，空格路径、以 `-` 开头的操作数，经过真实 `parseCliArguments` 后仍保持原值和位置。
- 用 Pi 宿主测试替身从确认流程调用到执行出口：同意时执行一次，拒绝、超时、无 UI 时零次启动；不能只测试一个裸参数函数。
- 在临时 Godot Editor 项目中验证 preview 不改属性，commit 实际修改，undo/redo 正确，删除只影响指定测试对象。清理会话保留仍存活或无法确认死亡的记录。
- 共用动作的 Pi、MCP 参数语义一致；测试只归一化临时路径等动态值，不掩盖授权差异。为公开动作与测试案例的对应关系做覆盖检查，避免新增动作漏掉一侧。

建议新增 `mcp/pi-contract.test.mjs`，扩展现有 `contract.test.mjs` 和隔离 Editor smoke。实际 Pi 宿主上的确认与执行另留一份验收记录；测试替身通过不能标为 Pi UI 已验收。

## R4 正确处理 watch 的错误状态

保留流式输出，累计已观察到的引擎错误状态。stdout 和 stderr 分别保留未结束行，进程结束时处理尾行，确保跨数据块的 `SCRIPT ERROR` 等标记不会漏检。

预期行为：

| 场景 | 操作结果 |
| --- | --- |
| 无错误，进程正常退出 0 | 成功 |
| 无错误，观察窗口按预期结束且清理成功 | 成功 |
| 出现错误标记，即使进程退出 0 或随后到达观察窗口 | 非零操作结果 |
| 启动失败、非零退出、取消或清理失败 | 保留对应生命周期结果 |

错误日志用于 watch 的操作状态和诊断，不能直接生成游戏测试 `FAILED` Verdict。日志不替代结构化断言证据。

建议新增 `mcp/watch.test.mjs`，覆盖完整行、跨块错误、无末尾换行、普通日志和正常观察窗口。每个流的未结束行须有界；超长日志的截断不能抹掉已识别的错误状态。CLI 验证通过后，补一项 MCP watch 调用，确认外层超时与内部观察窗口结束没有竞态误判；如需外层清理余量，单独明确其预算，不延长项目执行窗口。

## R2 让直接 CLI 超时有界

优先复用已有 `process-runner.mjs` 的 deadline、进程归属、TERM 到 KILL 升级和临时资源清理。嵌套调用消费剩余预算；已有 MCP 或 Pi 监督的调用不重复建立独立总预算。

先核对平台与启动入口：裸 CLI、`bin/gdeck.mjs`、Windows cmd/PowerShell wrapper，以及 `GDECK_CURSOR_COMPAT`、`GDECK_CODEX_DIRECT` 的优先级。Windows Agent Shell 的 Job Object 问题是此 fork 的既有约束，不能直接对所有平台关闭兼容模式。

对于必须直启的路径，使用能够继续响应计时器的异步启动与有界清理，并调整实际调用链等待结果。只把同步启动的信号改成 SIGKILL 不足以证明后代清理、取消和临时资源回收正确。先让 `run`、`check` 的窄用例通过，再接入 Unit、Scenario、Verify 等现有调用；避免保留两份不同的清理规则。

验证方法：

- 正常退出、非零退出、可响应 TERM、忽略 TERM、持有输出管道的后代、启动失败和大量输出。
- 直接 CLI 的默认兼容模式、显式 direct、显式 supervised；MCP 的超时、取消、断开；Pi 的取消路径。
- 等待夹具写出 readiness 与 PID 文件后再触发取消。超时用例先给出有界启动窗口并断言 readiness，避免引擎尚未启动就被杀死的假通过。
- 检查目标 PID、后代 PID 和归属临时目录均已清理。测试另设外部 watchdog 兜底；一旦该 watchdog 触发，用例必须失败，不能把兜底清理当成工具成功。
- 总耗时不得超过执行预算、清理预算与固定的测试调度余量之和。清理成功的执行超时保持 124，清理超时保持 125，启动失败保持 127；显式取消保留取消事实。
- Verify 的 deadline 传递、证据发布和中断分类仍有效；没有 terminal 报告时不能返回通过。

建议新增 `mcp/cli-process.test.mjs`，复用 `supervisor.test.mjs`、`session.test.mjs` 的夹具。macOS 验证可以先交付对应平台结果；Windows Agent Shell 与 Linux 原生运行分别记录，未经验证不得声称跨平台问题已关闭。

## R5 按职责拆分验证代码

先处理已出现双重维护的预算定义和参数转换。之后每次只移动一组完整职责及其资源所有权，不按行数切文件，也不建立新的通用插件框架。

建议拆分顺序与 Interface：

| Module | 对外职责 | 内部负责的事情 |
| --- | --- | --- |
| 参数转换 | 已校验动作转换为 argv | 位置参数、选项、默认值与操作数分隔 |
| 性能预算 | 校验预算并评估固定指标 | 指标定义、比较与换算 |
| 验证快照 | 创建执行快照并释放 | 复制、导入、封装、清理及准备耗时 |
| 验证报告 | 发布报告并返回产物引用 | 有界投影、JSON/Markdown、发布失败清理和 receipt |
| 验证执行 | 执行冻结计划并返回结果 | 阶段顺序、漂移检测、证据接纳与 Journal 生命周期 |
| CLI 入口 | 解析命令并设置退出码 | 参数分派及终端输出 |

优先沿现有 `verification-plan`、`result-envelope`、`evidence-journal` 的 Interface 拆分，隐藏内部文件句柄和清理顺序。一个资源只能有明确的释放方。共享模块不导入可执行的 CLI 入口，不通过反向依赖调用主文件；核心函数逐步返回结果，入口负责 `process.exitCode`。

验证方法：

- 对同一隔离夹具比较拆分前后：成功、断言失败、缺失或不完整报告、计划漂移、超时、发布失败的退出码、Verdict、classification、coverage 与产物是否一致。
- 先分别验证每份报告的实际哈希、invocation 绑定和 Journal 完整性，再归一化时间、耗时、临时路径进行语义比较；不能删除关键证据字段来获得对照通过。
- 移动快照代码时检查失败后目录清理；移动报告代码时用已有故障注入点检查半成品处理和旧产物保护。
- 验证执行仍涉及导出：使用模拟导出夹具覆盖成功、文件被修改、manifest 发布和回滚；只有实际改动平台导出行为时再运行对应真实导出。
- 新拆出的运行模块纳入 MCP `SERVICE_INFO.buildId` 的输入文件集合及随包分发检查；模块单独改变时，新服务指纹应改变。

完成标准是同一规则只有一个维护位置、旧实现被删除、相关失败路径通过。单纯把 5,905 行搬到另一个大文件不算完成；安装、Editor Bridge 等未受影响职责暂不扩大重构。

## R6 迁出项目专属 Oracle 流程

先搜索工具仓库、已知调用项目的脚本和使用文档，确认 `oracle-verify` 的真实消费者。把 19 个业务检查的顺序、超时和汇总移到所属项目，由该项目维护。

迁移期间保留旧入口，并明确其适用项目与迁移说明；消费者更新后再一起移除 CLI registry、Pi/MCP 动作映射、帮助和实现。不新增可执行任意脚本的通用 GDeck 扩展机制。未查明消费者时，R6 保持待迁移，不删除现有公开命令。

验证方法：在所属项目的隔离副本中，用固定的成功、失败、超时脚本验证流程顺序、汇总和退出码；切换调用方后再跑其原检查链。普通 Godot 项目的 help、describe、check 和 verify 不依赖这组业务脚本。没有消费者验收证据时，不把 R6 计为完成。

## 验证层级与运行方式

以下新增测试文件名为原计划建议，实施时已落地并增加 `verification-regression.test.mjs`。测试加入时同步更新 `mcp/package.json` 的显式 `test` 文件列表，避免本地单跑通过但默认回归遗漏。

| 层级 | 何时运行 | 验证内容与停止条件 |
| --- | --- | --- |
| 内容检查 | 本次计划、纯文档修改 | 路径、链接、命令、问题与验收映射、diff；不启动游戏 |
| 窄回归 | 每项行为修复 | 原失败用例先红后绿，并保留相关正常行为；通过后进入下一改动 |
| Node 回归 | 每个修订批次收尾 | 现有与新增契约、报告和生命周期测试；失败按原因处理，不通过重复运行取最好结果 |
| 真实 Godot | B、C 集成，以及 D 影响运行路径时 | 隔离 Editor smoke、Unit、Verify；A/B 套件在共享执行或报告路径受影响时运行 |
| 入口验收 | 改动对应适配层时 | CLI 实际进程、Pi 确认与执行、MCP 新会话及实际客户端连接 |
| 项目抽样 | 核心修订集成后 | 固定源码的 GreyRanger 隔离副本运行 fast；场景路径受影响时加一个现有短场景 |
| 平台验收 | 生命周期修订时 | macOS、Windows Agent Shell、Linux 分别留证；平台缺失单列 |

当前已有命令，从仓库根目录执行：

```sh
npm test --prefix mcp
GODOT_BIN=/Applications/Godot.app/Contents/MacOS/Godot npm run test:godot --prefix mcp
```

第二条路径仅适用于相应 macOS 安装。测试会创建临时项目与隔离用户目录；所有游戏抽样也使用独立副本，避免读取真实玩家存档。项目 fast 只能证明其实际配置的阶段；不以 fast 代替 Editor、性能预算、导出或长测验收。

MCP 验收先用源码新服务测试集成。安装交付涉及服务、加载依赖或 schema 时，再通过实际客户端重连核对 version、buildId 和结构化结果。CLI-only 更新且 MCP 契约未变时，不把重连作为普通 CLI 验证的前提。

## 交付记录与总体完成标准

每个修订批次记录源码提交、Node/Godot/OS 版本、入口与兼容模式、实际命令或请求、预期与实际结果、日志和报告位置。过程中的失败保留原因；只把修订后匹配源码的结果作为验收依据。

- R1 至 R4 均有失败复现和修复后通过证据，且默认测试命令包含这些用例。
- R3 的确认拒绝路径没有启动写操作；R2 的测试不需要外部 watchdog 救场。
- R5 完成既定职责迁移、删除重复实现，报告语义和失败清理对照通过。
- R6 有消费者迁移验收，才允许删除兼容入口；否则保留单独的未完成状态。
- 适配入口和平台按实际覆盖结论交付，不以 Node 通过替代 Pi UI 或 Windows 认证。
- 新增运行依赖目标为 0；代码净增减在完成后统计。测试、文档与运行代码分别列出，不用删行数代替正确性。

本次已实施运行代码修订并保留分批提交；未更新全局安装、实际客户端连接或真实游戏项目，版本号保持 `1.6.8`。R6 的消费者迁移与未具备环境的平台验收保持开放。
